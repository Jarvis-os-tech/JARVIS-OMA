## 6. Important conflicts resolved during consolidation

**Service ownership.** The old master identifies `jarvis-oma.service`; the current JARVIS OS CLI and service source identify `jarvis-voice.service`, with separate bridge/monitor/task services. The target invariant is one microphone owner and coherent lifecycle contracts, not an assumption that every subsystem must share one process or that an old service name remains canonical forever.

**IPC.** The active voice source resolves a private user-runtime `jarvis/control.sock`; older plans use `/tmp/jarvis.sock`, `/tmp/jarvis_ipc.sock`, `/var/run/...` and other paths. Source discovery/configuration must resolve the installed contract. The master does not instruct components to create competing legacy sockets.

**Voice defaults.** `jarvis_voice/config.py` currently declares `barge_in=False` and `turn_silence_frames=50`. The daemon uses the configured value; 50 capture frames at 20 ms represent one second. The voice-foundation guide describes an earlier 15-frame/300 ms endpoint. These are source/default/document differences, not a measurement of the installed user's current configuration. The master therefore requires measured endpointing and explicitly distinguishes availability from enabled behavior.

**AEC and continuity.** The current daemon imports `MonitorEchoCancellation` from `jarvis_voice/echo.py`, while older guides describe half-duplex holdoff as the principal safeguard. The required product behavior is proven echo-safe interruption; neither an older guide nor an AEC module's presence establishes physical acoustic quality.

**Agent durability.** Earlier Hermes implementation notes say parent cancellation and independent goal supervision are future work. Current source includes `DurableHermes`, native receipts, owner generations and parent-worker cancellation. `skills/domains/orchestration.py` constructs the durable adapter, and tests cover these contracts. They are existing software foundations with live/integration scope still to be established per workflow, rather than universally absent features or proof of faultless operation.

**Installed runtime.** The older README describes a checkout-linked installation. Read-only inspection found `~/.local/bin/jarvis` resolving through `~/.local/share/jarvis-runtime/current/bin/jarvis`, with current/previous release links present. That establishes filesystem layout only, not the running process's loaded revision or successful end-to-end rollback. The master retains decoupled releases as the target contract.

**Island wiring.** The copied active project's `ui/omarchy-jarvis-island/AgentBridge.qml` still invokes absolute helper paths in `/home/g0pi/Projects/JARVIS-OMA`, including legacy status/control scripts. It cannot be assumed to consume the new voice socket merely because its visual source exists. Bridge migration and live UI validation remain work to verify.

**Release health and data recovery.** The current release manager checks service activity and snapshots top-level runtime-data databases using file copies. A successful status check or copy does not prove application readiness or a consistent backup of every live memory/task database. The final master requires stronger tested readiness and state compatibility before the managed OS release gate.

**Security metaphors.** A token filter, persona named Ultron, “absolute” screen awareness, a sandbox label, or “kernel executes intents” is not accepted as a literal trust boundary. These become typed validation, authenticated policy, scoped observation, real isolation, and OS adapters.

**Resource and time claims.** Earlier documents disagree on free RAM, filesystem, partitions, hostname and CPU allocation; some promise zero-resource perception, instantaneous reconnection or universal microsecond behavior. These remain unverified historical claims. The master requires a current hardware baseline and scoped measurements, without a blind hardware rewrite or a fixed 70-day commitment.
