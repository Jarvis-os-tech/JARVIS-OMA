# OpenAI evidence review and architecture debate

Research checked 14 October 2026. This report separates published evidence, limitations, and our proposed engineering choices. It does not certify any system as AGI.

## What OpenAI actually publishes

**Astra is a documented model.** OpenAI publishes a GPT-6 Astra announcement, system card, and API model page. The announcement describes advances from pretraining, reinforcement learning, and alignment, and reports computer-use and reasoning results. It also explains that benchmark results depend on evaluation environment and settings. These are vendor-reported measurements, not proof of universal competence or independent reproduction. Searching the official material reviewed here did not locate a reproducible recipe containing the architecture, complete training data, training code, weights, and compute configuration needed to recreate Astra. That is a bounded search finding, not proof that no further material exists. [Astra announcement](https://openai.com/index/gpt-6-astra/)

**Jarvis can integrate the model, but cannot fine-tune Astra through the documented API.** The model page lists text input/output, image input, function calling, structured outputs, and computer use. It explicitly lists audio and fine-tuning as unsupported. Therefore, voice should use a separate speech interface connected to the reasoning controller. An API integration changes Jarvis’s behavior and available tools; it does not grant access to the hosted model’s weights or training pipeline. Recheck feature availability when implementation begins. [API model reference](https://developers.openai.com/api/docs/models/gpt-6-astra)

**AI research assistance is demonstrated under specific constraints.** The system card describes NanoGPT training optimization with one H100 GPU, and PostTrainBench Lite experiments using small pretrained models and five hours. It explicitly warns that the small pretraining task does not demonstrate the ability to design and operate frontier-scale pretraining. These evaluations support investigating bounded automated ML experiments; they do not establish that a deployed assistant recursively upgrades its own frontier intelligence. [Astra system card](https://deploymentsafety.openai.com/gpt-6-astra)

**Some training methodology is disclosed.** OpenAI’s Ironclad collaboration uses expert-selected workflows, detailed outcome criteria, hosted practice environments, synthetic tasks, and reinforcement learning. Its reported evaluation covers 11 tasks; time savings are simulated estimates. The transferable idea is to define realistic tasks and externally inspectable success before optimizing. This is a methodological example, not a complete model-building recipe or evidence that reinforcement learning is the cheapest first improvement for Jarvis. [Ironclad research](https://openai.com/index/advancing-computer-use-with-ironclad/)

**Harness improvements can resemble intelligence gains.** OpenAI reports substantial ARC-AGI-3 changes after enabling retained reasoning and compaction. Those changes concern execution context rather than new model training. Jarvis should preserve task state and evaluate context-management changes, while describing resulting gains accurately as system-level improvements. Benchmark names containing “AGI” do not establish an agreed universal AGI threshold. [ARC-AGI-3 harness study](https://openai.com/index/how-two-settings-tripled-our-arc-agi-3-scores/)

## Debate and decisions

**Hosted reasoning model versus training our own foundation model.** Training offers weight ownership and potentially specialized behavior. The counterargument is that no reviewed source supplies a reproducible Astra recipe, and training introduces a separate data, infrastructure, and evaluation program. Decision: begin with a replaceable hosted reasoning backend, measure bottlenecks, and only later compare a suitable trainable model on a narrow task. Do not make foundation-model training a prerequisite for a useful Jarvis. This is our engineering recommendation, not an OpenAI claim.

**Many agents versus one controller.** Specialists can independently research and inspect proposed plans. Shared desktop mutation creates races: one worker’s observation becomes invalid after another clicks or changes focus. The desktop reviewer challenged any assumption that integration documentation establishes a universal API/DOM/vision accuracy ordering; accepted. Test tool routes per task. We jointly recommend one active desktop owner, explicit handoffs, fresh observations after handoff, and parallel workers limited to read-only research or isolated environments. Compare advisors against a single-controller baseline under the same model, tools, task seeds, time, and token budget. More agents is a hypothesis to test. OpenAI likewise recommends letting evaluations determine whether multi-agent complexity is justified. [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

**Daily self-improvement versus daily unverified change.** The learning reviewer challenged whether memory gains merely retrieve existing competence or spend more inference. Accepted: record model identity and version when available; freeze candidate artifacts before testing; use equal-budget comparisons and memory/skill-disabled ablations. Keep task families unseen during optimization. Candidate-generated tasks may aid practice, but should not independently certify release quality. A daily cycle can legitimately end with no promoted update.

**What would count as improvement?** Proposed release evidence includes paired outcomes on held-out tasks, uncertainty intervals, predefined meaningful improvement and noninferiority thresholds, stable cost and latency limits, and no permission-boundary failures. Cap submissions against a sealed set and refresh audit batches to reduce benchmark overfitting. Prefer artifact/state verification over an agent declaring success. Log whether a gain came from retrieval, tools, workflow, inference budget, or actual weight changes. These proposals require local experiments; no experiment in this review proves their benefit for the current repository.

## Build implication

First build measurable authorized task execution, then verified memory and reusable skills, then isolated candidate development and release evaluation. Keep voice responsive and stoppable throughout. Treat broader generalization as a research objective measured on unfamiliar tasks—not a product label earned by adding permissions, agent counts, or an overnight scheduler.
